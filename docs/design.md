# 设计与计算约定

## 目标

让用户在网页、聊天及不同 Agent 之间使用同一份预算状态。模型负责理解明确的用户请求，确定性引擎负责记账、计算和定时事件。

产品参考：[Actual 的信封预算](https://actualbudget.org/docs/)，[Firefly III 的预算工具](https://docs.firefly-iii.org/how-to/firefly-iii/finances/budgets/)。本项目聚焦每日额度与两个可消费资金池，不复刻其完整财务软件，不使用其源码。

## 资金与额度不是一回事

每日额度只是一条限额规则，不是每日凭空增加的资金。消费 A 从日常池发起时：

1. 当天未用额度 = max(0, 日限 − 当天日常消费)。
2. 日常承担 = min(A, 当天未用额度, max(0, 日常池余额))。
3. 灵活承担 = A − 日常承担。
4. 消费总额仍计入当天日常用量。直接指定灵活池 / 保底池的消费不计入日常用量。

结算时将剩余额度从日常转给灵活，但不超过日常实际余额。已在消费时承担的超额不再结算扣一次。撤销和补记会重算已结算日；撤销较早消费可能释放后续消费的日常额度，系统会用 `coverage` 分录重新分配承担额。

真实支出允许负余额。可消费合计 ≤ 0 触发红色状态和一次通知事件。保底池仅在明确选择或转账时改变。

## 存储

- SQLite WAL + `BEGIN IMMEDIATE`，写入串行化。
- 所有金额为整数分；输入只接受最多两位小数的字符串。
- `entries` 表记录用途与来源，`postings` 记录成对的资金变化，每一笔合计为零。收入、支出通过 `external` 对手科目平衡。
- `requests` 以调用者和幂等键去重；键相同、正文不同返回 409。
- 软性额度与真实支出分离，不把超支漏记成零。
- 对账保存当时的期望值与实核值；后续补记使期望值变化时显示过期状态。

## 时间

- 每本账一个固定 IANA 时区，起始日为初始化当天。
- 日限规则按生效日期版本化，不能向过去生效。
- 每日额度零点重置，结余按配置时间结算；两者分开显示。
- 入账计划使用当地日历，月末短月取最后一天。
- 修改计划从当天生效。已经入账的同一日期不重复入账；未执行过的当天到期计划可执行。
- 服务每 30 秒补跑到期任务，事件和入账在一个事务中提交。服务停机期间无外部调度保证，恢复后补记。
- DST 重叠时间按当地日期去重，缺失时刻在后续检查中补跑；本版主要在 Asia/Shanghai 测试。

## 交互

主题、形态、配色属于浏览器偏好，不进入账本。额度条只反映数据；收入到资金池不会虚增当天的限额。粒子动画仅在成功记账后局部呈现，尊重减少动态效果设置。

通知为 outbox，不直接硬编码聊天平台。生成、投递、确认是三件事。平台暂时失败不能把事件标记为已送达；只指定一个通知代理，并用事件 ID 防重。

## 范围

一个实例一个所有者。不同用户应部署隔离实例与数据目录。本版没有多租户权限模型，不能把一个实例当公共记账平台。MCP stdio、REST、function-calling 是互通边界，不宣称所有厂商插件商店均已验证。
